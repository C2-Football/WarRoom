## Material finding and bounded correction

**High: delayed automatic OAuth restoration replaced a newer explicit account.** The production login script checks an existing app session before awaiting `db.auth.getSession()`, but originally did not revalidate after that await. Actual-script/actual-account-helper VM reproduction: email account B signs in successfully; an older SDK restore for OAuth A then resolves; `fw_session_v1` becomes OAuth A, context owner changes to `oauth:older-oauth-a`, and the page redirects to onboarding. A late rejection also overwrote the successful sign-in message.

Fix lives in isolated branch `codex/readiness-oauth-restore-20260918`, based on `c288d84`: explicit email/legacy/signup and new OAuth requests advance a request version. Automatic restore checks that version after the SDK await and before publishing a session or navigating. It also compares both stored auth sessions with their initial snapshots, so a session installed by another tab survives. Cancellation persists through a failed explicit request; a late restoration error cannot replace an explicit result.

Regression first failed on the original source (`undefined !== 'b'`, restored OAuth replacing B), then passed with the fix. The harness executes the full production inline script plus real account-storage helper. It covers delayed OAuth session/rejection after successful email sign-in, a restore while manual sign-in is still pending, failed manual sign-in, explicit new OAuth navigation, and another tab installing account B. The previous 20 restoration scenarios still pass, including ordinary returning OAuth, game-entry identity rules, expired sessions and quota failure. Account-storage and account-session suites also pass. Independent security-owner review and root candidate rerun remain integration gates.
